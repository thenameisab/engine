- **Migration 0016 `user_credentials`**, applied to live Neon (project `wispy-butterfly-72568636`, now 16 applied). Keyed by `user_id`, not email, and that is the load-bearing choice: the principal id is `local:<lowercased email>`, *derived*, so a lookup needs no unique index on `users.email` — an index that does not exist and cannot be added safely, since Neon Auth rows may legitimately repeat an address across providers. Applied through the repo's own bookkeeping (version/name/sha256 checksum computed the same way `plan.ts` does), not an ad-hoc insert, so the runner does not see drift on the next `migrate`.
- **`packages/auth/src/passwordHash.ts`**: PBKDF2-HMAC-SHA-256 via WebCrypto. bcrypt/scrypt/Argon2 are better primitives and none is available on Workers without shipping WASM into a bundle already at 456 KiB. Stored form is self-describing — `pbkdf2-sha256$<iterations>$<salt>$<hash>` — so the work factor is raisable without a migration and a future `argon2id$…` is a new branch in `verifyPassword`, not a rewrite.
- Iteration count is **100,000**, not OWASP's 600,000, and the reason is a real constraint rather than laziness: this derivation runs inside a Workers request with a CPU ceiling, and exceeding it does not slow sign-in down, it fails the request — a worse security outcome, because the fix people reach for is turning the hashing off. `needsRehash` upgrades each password on its owner's next successful sign-in, which is the only moment the plaintext exists to re-derive from. **Unverified on the real Workers runtime** — no way to measure it from this sandbox; if sign-in starts timing out, that number is the first suspect.
- **`POST /auth/login` reads the database first, the roster second, and the database wins.** A stored credential that fails to verify is a failed sign-in, full stop — it does not fall through to `LOCAL_AUTH_USERS`. Without that rule, changing a password in Neon would not actually change it: a stale roster entry in the Worker secret would keep admitting the old one and nothing would report the conflict. The roster survives only as a fallback for addresses with no stored credential, so local dev works with no database and the cutover did not have to be atomic.
- Timing was the fiddly part. PBKDF2 is deliberately slow, so an unknown address that returns early is measurably faster than a wrong password — tens of milliseconds, observable over the network, and the thing it leaks is which of three people's addresses are real. Hence `dummyHash()`: a syntactically valid hash nothing verifies against, derived against on every miss. Its test asserts it is *parseable*, because an unparseable one would make `verifyPassword` bail before deriving and quietly restore the gap.
